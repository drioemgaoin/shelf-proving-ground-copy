# Test Level Decision Tree

Choose the cheapest level that catches the defect. Walk top to bottom — stop at the first match.

## Unit

**Use when:** the behavior is a pure function or a single module with no I/O, no child processes, no file system, no network. The seam is a function signature.

**Examples:** `validateFinding()`, `parseFindings()`, `sortFindings()`, `findCurrentInFile()`, `applyPatch()`, `parseEnforcementBlocks()`, `estimateTokens()`.

**Characteristics:** fast (<100ms), no setup, no teardown, no mocking. Expected values are literals from the spec — never computed by the test.

## Integration

**Use when:** the behavior crosses two or more parts: a script reads files and produces output, a hook receives stdin JSON and exits with a code, a parser reads rules files and generates payload directories. The seam is a CLI interface (stdin/stdout/stderr/exit code) or file I/O boundary.

**Examples:** `apply-t1.mjs` (stdin JSON → exit code + stderr), `apply-t3.mjs` (rules files + git diff → payload files), `audit-rules.mjs` (rules files → exit code + stdout), `apply-fixer.mjs` (findings file + source files → patched files + JSONL), `expand-prompt.mjs` (template + vars → expanded prompt).

**Characteristics:** creates temp directories, writes fixture files, spawns child processes, asserts exit codes and file contents. May need mock `git` in PATH for tests that call git internally. Typical runtime 100ms–5s.

**Mock strategy:** mock external dependencies (git, dev server, network) via PATH override or env vars. Never mock the module under test.

## Integration with mocked dependencies

**Use when:** the behavior is in a function that calls external services (SDK, Docker, tracker API) but whose core LOGIC — branching, escalation decisions, loop termination, routing — can be verified by replacing the external call with a test double. The seam is the function signature; the mock replaces the dependency, not the function under test.

**Examples:** `runGateLoop()` (mock `timedSandboxRun` → verify escalation after 3 rounds, DEFER handling, oscillation detection trigger), `executeInParallel()` (mock sandbox → verify parallel dispatch and result filtering), `escalate()` (mock `execSync` → verify tracker commands called with correct args).

**Characteristics:** imports the real function, replaces one or two dependencies via dependency injection, module-level stubs, or parameter overrides. Asserts on return values, side effects (calls to mocked dependencies), and state changes. Does NOT require Docker, running services, or network access.

**Mock strategy:** inject mocks via function parameters, module-level stubs, or test-scoped overrides. The test verifies the function's decision logic, not the external service. If the function doesn't support injection, note this in the gap entry — the tdd skill may need to refactor for testability.

## End-to-end (E2E)

**Use when:** the behavior requires a running application — a browser loads a page, interacts with UI elements, and asserts visible results. The seam is the browser viewport.

**Examples:** Playwright tests in `e2e/` and `qa/invariants/`. Fixture system (`?fixture=`) controls app state.

**Characteristics:** requires dev server, Playwright browser, takes seconds per test. Use only when the behavior cannot be verified at a lower level.

**Structural alternative:** when you need to verify that a generated test file covers the right matrix (viewports, fixtures, assertions), read the file and assert its structure at integration level instead of running the full E2E suite.

## Acceptance

**Use when:** the behavior is a user-facing contract or a full pipeline flow. Two kinds:

1. **UI acceptance** — declared in a ticket's acceptance criteria, generated by `ui-contract` from T2 enforcement blocks and locked in `e2e/acceptance/`. If missing, report as a missing T2 enforcement block.

2. **Pipeline acceptance** — a full lifecycle test proving the orchestrator works end-to-end: ticket enters → phases execute → ticket closes or escalates. These do NOT require a browser. They run against mocked agents with real file I/O, verifying the composition of all components that unit and integration tests cover in isolation.

**Pipeline acceptance tests are the highest-value gaps** because they catch integration failures invisible at every lower level. If the unit tests for `isClean`, `findingsOverlap`, `runGateLoop`, `escalate`, and `runQAGates` all pass individually, but the wiring between them is wrong, only a flow-level test catches it. Always ask: "is there a test that proves the happy path works? The escalation path? The re-queue path?"

## Coverage depth — a single behavior may need tests at multiple levels

Do not stop at the cheapest level. Walk up the call chain:

1. **Leaf function tested at unit level** — proves the function logic. Catches: algorithm bugs, off-by-one, wrong regex.
2. **Caller tested at integration (mocked) level** — proves the composition. Catches: wrong arguments to the leaf, wrong branch on return value, missing call, wrong call order.
3. **Full flow tested at acceptance or e2e level** — proves the contract. Catches: integration failures invisible to lower levels.

**Report gaps at each missing level separately.** If `isClean()` is unit-tested but `runGateLoop()` calling it is not, report the gate-loop gap — it catches a different defect class.

## Decision shortcuts

| Signal | Level |
|--------|-------|
| Exported function, no I/O | Unit |
| Script with exit codes | Integration |
| Script that reads/writes files | Integration |
| Hook that receives stdin JSON | Integration |
| Function with decision logic that calls external services | Integration (mocked) |
| Orchestrator routing, escalation, loop termination | Integration (mocked) |
| Ticket status transition, label policy, phase gating | Integration (mocked) |
| Gate loop: verdict → escalation → next-round decision | Integration (mocked) |
| Merger eligibility check | Integration (mocked) |
| Behavior visible in browser | E2E |
| Ticket acceptance criterion | Acceptance (generated) |
| Generated file must have correct structure | Integration (structural) |
| Hard limit boundary (N passes, N+1 triggers) | Same level as the code that enforces the limit |
| Full pipeline: ticket enters → phases → closes/escalates | Acceptance (pipeline) |
| Escalation → re-queue → re-entry flow | Acceptance (pipeline) |
| Global T2 child bug: create → dedup → auto-close | Acceptance (pipeline) |
