# Tone Rules for Spec Writing

These rules apply to ALL spec types. They come from frontier consensus (Google Developer Docs, GOV.UK, Stripe, Amazon, Basecamp, IETF, plain language research -- 80%+ agreement).

1. **Active voice. Name the actor.** "The hook blocks the file." not "The file is blocked."
2. **One idea per sentence. One topic per paragraph.** Target 15-25 words per sentence.
3. **Front-load the important point.** First sentence of every paragraph carries the key fact.
4. **Concrete over abstract.** Give the number, the name, the exit code. Kill "appropriate," "various," "certain," "properly."
5. **Use "the [component]" as subject, "you" for the reader.**
6. **No jargon without inline definition.** Definition in parentheses or dash clause, on first use.
7. **Show structure first.** Table or list before prose explanation.
8. **State the rule, then the reason.** Not the other way around.
9. **Flat hierarchy.** Max 2 heading levels (## and ###). If you need a third, split the section.
10. **No hedge words.** Commit or flag as open. "The system retries once." not "should probably retry."
